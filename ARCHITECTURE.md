# ARCHITECTURE.md — предлагаемая архитектура

**Статус:** проектирование с нуля; это предложение, не реализованная архитектура. Технические предположения помечены явно.

## 1. Решения верхнего уровня

- SwiftUI для UI, единое приложение iOS, без сетевого слоя и сторонних сервисов.
- Предлагаемое хранилище: **SwiftData** (iOS 17+), если минимальная поддерживаемая iOS версия будет 17 или выше. Причины: системный локальный persistence, связи моделей, транзакционное сохранение и интеграция с Apple-платформой при умеренном размере домена. Для JSON backup использовать отдельные `Codable` DTO, не сериализовать внутренние модели SwiftData напрямую.
- Техническое предположение: SwiftData migration и операции полной замены/транзакций должны быть проверены на выбранном target iOS. Если продукту нужна поддержка ниже iOS 17 либо детерминированное переносимое хранилище, рассмотреть SQLite/Core Data до реализации; не добавлять абстрактные слои заранее.
- Одно активное выполнение тренировки. Его состояние хранится в локальной модели и обновляется автоматически, а не в отдельном пользовательском «черновике».
- Производные статистики вычисляются из завершённых записей; не дублировать агрегаты в базе без доказанной проблемы производительности.

## 2. Слои и потоки

```text
SwiftUI Views (4 вкладки, детали)
        ↓ actions / observed state
Feature State & ViewModels (Home, Workout, Progress, Statistics, Settings)
        ↓ domain operations
Services (WorkoutSession, Metrics, Water, Notifications, Backup/Restore)
        ↓ repositories / SwiftData ModelContext
Local SwiftData store
```

Статические шаблоны тренировок и каталог упражнений — встроенный каталог с устойчивыми строковыми ID. Пользовательские изменения техники и настройки — локальные данные. Изображения — локальные Assets. UI не вычисляет тоннаж самостоятельно: вызывает общий `MetricsService`/чистые доменные функции, используемые и статистикой, и тестами.

Предлагаемая структура групп (не существующие файлы): `App`, `DesignSystem`, `Domain`, `Data/Persistence`, `Features/Home`, `Features/Workout`, `Features/Progress`, `Features/Statistics`, `Features/Settings`, `Resources/Assets`, `Tests`.

## 3. Сущности и связи

Все пользовательские сущности имеют UUID, даты — ISO-совместимые даты; веса хранятся числом в кг с фиксированной точностью (предлагается Decimal либо целые граммы), рост — см. Формат и округление должны быть единообразны.

- **WorkoutDefinition**: стабильный `workoutID` (например `workout_1`), имя, упорядоченный список ExerciseSlotDefinition. Встроенный каталог; не копировать для каждого пользователя.
- **ExerciseDefinition**: стабильный `exerciseID`, каноническое имя, `assetName`. 15 элементов общего каталога.
- **ExerciseSlotDefinition**: стабильный ID позиции и ссылка на exerciseID; позиции тренировок определяют порядок, повторения указывают на тот же ID упражнения.
- **WorkoutSession** (единственная активная): UUID, workoutID, startedAt, updatedAt, currentSlotID/index, состояние позиции и список SessionExercise. Изменения записывать сразу. Валидировать, что существует максимум одна активная сессия.
- **SessionExercise**: slotID, templateExerciseID, actualExerciseID (по умолчанию совпадают), `isReplacement`, статус (`pending`, `inProgress`, `completed`, `skipped`), порядок, подходы.
- **WorkoutRecord**: UUID, workoutID, startedAt/finishedAt, снимок названия и порядка шаблона. Содержит дочерние RecordExercise. Не связан с текущим содержимым каталога так, чтобы изменение каталога переписывало старое.
- **RecordExercise**: templateExerciseID и фактический exerciseID, имя-снимок, слот, статус, упорядоченные подходы. Это неизменяемый после сохранения снимок выполнения, кроме будущего явно определённого редактирования истории.
- **SetEntry**: порядковый номер, статус (completed/skipped/incomplete), масса и повторы nullable. Пустые поля не равны выполненному подходу.
- **BodyMeasurement**: UUID, тип (`weight`/`height`), значение, единица/каноническая единица, measuredAt, createdAt. Изменение текущего значения добавляет запись; исправление ошибочной записи — явная операция.
- **WaterDay**: локальный `dayKey` календарной даты и consumedMl (целое, 0…3000), updatedAt. Один уникальный ключ на день; атомарное прибавление 200 мл с saturating cap 3000.
- **ExerciseInstruction**: exerciseID, пользовательский текст, updatedAt. Один актуальный текст на каноническое упражнение.
- **AppSettings**: напоминания включены/выключены и иные пользовательские параметры; разрешение ОС хранится ОС и не подменяется флагом приложения.

История WorkoutRecord содержит названия и значения на момент завершения (снимки), поэтому обновление шаблона или названия не изменяет прошлые записи. Повторные упражнения ссылаются на общий ID, а не дублируют определение/картинку.

## 5. Сессия, автосохранение, восстановление

Каждая правка поля/статуса/позиции сначала обновляет модель сессии и сохраняется через ModelContext. Для ввода с высокой частотой допускается короткая debounce-запись, но при уходе в background, закрытии экрана и смене позиции выполнить немедленный save; финальная гарантия должна учитывать аварийное завершение, поэтому предпочтительно сохранять изменения немедленно или с минимальной задержкой и тестировать восстановление.

На старте приложения искать активную сессию. Если найдена — восстановить введённые значения и selected slot. Если нет — обычная главная. При старте новой сессии существующая должна быть возобновлена либо пользователь должен явно подтвердить отказ от неё; тихо терять данные нельзя. Завершение выполняется атомарной операцией: построить immutable WorkoutRecord, вставить запись, удалить активную сессию и сохранить транзакцию. При ошибке транзакции активная сессия остаётся.

## 6. Расчёты

- **Тоннаж подхода:** `weightKg × repetitions`; сумма только для подходов `completed` с обоими валидными положительными значениями. `skipped`, `incomplete`, пустые значения исключаются. Не умножать повторно на число подходов: каждый SetEntry — отдельный подход.
- **Тоннаж тренировки/дня/всего:** сумма тоннажа валидных выполненных подходов по завершённым WorkoutRecord. Разрешить завершение с пропусками, они ничего не добавляют.
- **Число завершённых тренировок:** число записей WorkoutRecord, сохранённых явной кнопкой завершения; наличие нулевого тоннажа не отменяет завершение.
- **Выполненные подходы:** число SetEntry со статусом completed и валидным вводом согласно выбранному правилу; продуктово подтвердить, считать ли выполненным подход с повторами, но без указанного веса. Рекомендация: статус completed задаётся явно, тоннаж требует обоих полей, счётчик подходов считает completed независимо от веса.
- **Частота:** локальные календарные интервалы; неделя по Calendar.firstWeekday, месяц по локальному календарю.
- **Лучший день:** сумма дневного тоннажа; детерминированное разрешение ничьей — более ранний день.
- **Вода:** stored consumedMl capped at 3000; «осталось» = max(0, 3000−consumedMl). Очистка записей старше 7 локальных календарных дней при старте/смене дня.
- **Прогресс тела:** выбор последней датированной записи на каждую дату, статистический диапазон последних 12 месяцев; поздние/исправленные записи сортируются по measuredAt.

## 7. Локальные уведомления

`UNUserNotificationCenter` и календарные локальные триггеры, без сервера. Планирование слотов 09:00, 11:00, 13:00, 15:00, 17:00, 19:00, 21:00, 23:00 по локальному времени (всего 8). Уведомления не должны дублироваться при повторном планировании: стабильные identifiers, сначала отменить принадлежащие приложению запросы, затем создать актуальные. Учитывать отказ, отзыв разрешения, смену даты/часового пояса и отключение настройки. Точный механизм повторения через переходы часового пояса подтвердить на iOS; показывать разрешение только после пользовательского намерения включить напоминания.

## 8. JSON экспорт/импорт и миграции

Определить независимый `BackupDocument` с `formatIdentifier`, `formatVersion`, `createdAt`, `appVersion` и секциями каталога пользовательских данных: записи тренировок, измерения, WaterDay в текущем окне, инструкции, настройки, активная WorkoutSession. Статические шаблоны можно хранить в backup как ID/версию каталога для совместимости, но импорт не должен позволять перезаписать встроенный каталог исполняемыми данными.

Экспорт: получить согласованный снимок локальной БД, сформировать Codable DTO, кодировать UTF-8 JSON, проверить, что файл читается обратно, передать документ-пикеру/share sheet. Импорт: лимит размера; декодирование; версия; обязательные поля/диапазоны; уникальность UUID и dayKey; ссылки на известные IDs; проверка единственной активной сессии; миграция DTO старых версий к текущей; построение временного набора; затем транзакционная полная замена. При ошибке до/во время commit исходное состояние сохраняется/откатывается. После успеха обновить уведомления по настройкам. Не импортировать пути к файлам/произвольные ресурсы.

Версии схемы backup и persistent schema раздельны. Добавлять последовательные миграции N→N+1; неизвестную более новую backup-версию отклонять с понятным сообщением. До каждой миграции иметь автоматические тесты fixture-файлов и проверку отката.

## 9. GitHub Actions и IPA — проектное предложение

Workflow `iOS CI` запускается на push/PR и вручную на `macos-latest` либо закреплённом поддерживаемом macOS runner. Порядок jobs/steps:

1. checkout исходников, определить Xcode и показать его версию;
2. установить/выбрать поддерживаемую Xcode (без личных сертификатов);
3. проверить форматирование (например, SwiftFormat только если инструмент будет утверждён/зафиксирован), статический анализ и тесты;
4. собрать нужную схему для generic iOS device с `CODE_SIGNING_ALLOWED=NO`/эквивалентом, подтвердив конкретные параметры на выбранной версии Xcode;
5. сформировать `.app` и упаковать `.ipa` по документированному unsigned-процессу;
6. проверить ZIP/IPA структуру, наличие Payload/*.app, ожидаемого bundle ID/ресурсов, отсутствие неожиданных профилей/сертификатов и успешное тестовое распаковывание;
7. загрузить IPA и отчёты как GitHub Actions Artifact.

Не хранить provisioning profile, `.p12`, пароль сертификата и ключи в GitHub Secrets. Не включать automatic signing личным сертификатом. Разделить CI validation и IPA packaging, чтобы сбой упаковки был диагностируем. Хранить workflow минимальным и фиксировать версии actions в соответствии с политикой проекта.

**Критическое техническое предположение:** `CODE_SIGNING_ALLOWED=NO` и ручное архивирование могут дать IPA, но установимость/пригодность для ESign и отсутствие нужных метаданных зависят от Xcode и ESign. Требуется проверить на реальном macOS runner и целевом процессе ESign до объявления канала рабочим. Xcode может требовать подпись на отдельных стадиях; нельзя обещать unsigned IPA до прототипа. ESign самостоятельно выполняет пользовательскую подпись; CI не принимает сертификаты. Конкретные версии Xcode, macOS, iOS target, actions и команды не фиксированы до создания проекта и проверки.

## 10. Ошибки, безопасность и тестируемость

Ошибки persistence, backup, разрешений и URL открываются как понятные UI-состояния; не терять активную сессию при ошибке. JSON импортировать только после полной проверки. Данные остаются внутри sandbox приложения; системное шифрование устройства — ответственность iOS. Не обещать отдельное шифрование/защиту backup без утверждённого требования. Чистые функции тоннажа/частоты тестировать unit-тестами; persistence, миграции, restore, переход даты и notification scheduling — интеграционными тестами.

## 11. Решения, требующие утверждения/проверки

1. Минимальная iOS 17+ и SwiftData либо более низкий target с другой технологией.
2. Фактический критерий выполненного подхода для счётчика, если вес не внесён; предложено считать явный completed.
3. Называние двух позиций тренировки 2 («Махи на плечи», «Присед в гакке») относительно доступных PNG/канонического каталога.
4. Разрешать ли удалить один из двух начальных подходов.
5. Метрика графика (тоннаж упражнения за сессию рекомендуется) и число последних тренировок.
6. Ограничение одной незавершённой сессии.
7. Практическая упаковка/установка unsigned IPA и ESign; проверить на выбранной версии Xcode.

## Implementation status note (2026-11-08)

An initial SwiftUI implementation was added. It currently uses an atomic Codable JSON file in Application Support instead of SwiftData, because full-state replacement during import and crash-safe active-session persistence are straightforward to implement with one atomic file. This is a deliberate implementation deviation from the original proposal and still needs macOS validation. The app and CI have not yet been compiled or run in this Windows environment. The unsigned IPA workflow only packages an unsigned app and does not claim ESign install compatibility.

### Import safety and local-store recovery implementation

The current JSON implementation validates format identifier/version, unique IDs, measurement and water ranges, known workout/exercise IDs, session cursor and minimum set counts before import. Restore writes the fully encoded replacement to the same file with `Data.write(options: .atomic)` before changing observable in-memory state, so decode/validation/write failures leave existing data unchanged. When the persisted local file cannot be decoded or validated at launch, automatic water rollover/save is suppressed to avoid overwriting the original file; subsequent automatic saves are blocked until a valid import succeeds. This is a simple single-file transaction boundary; tests cover malformed import preservation and corrupt local-file preservation. Device-level crash/power-loss behavior still requires macOS/iOS execution.
